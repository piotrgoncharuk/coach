# Coach

Личный дневник тренировок: зал, футбол, прогресс. PWA для iPhone и Mac, интерфейс на русском,
килограммы и сантиметры. Два независимых пользователя (Пётр и Юлия), данные полностью изолированы.

**Живой адрес:** https://piotrgoncharuk.github.io/coach/

## Что умеет

| Раздел | Что внутри |
|---|---|
| Сегодня | план дня из календаря, старт тренировки, футбол одним касанием, утренний чек-ин и готовность, белок и калории, серия недель, заметка тренера, конфликты недели |
| Тренировка | подход одним касанием (вес и повторы из прошлого раза по двойной прогрессии), таймер отдыха по метке времени, замена на аналог, суперсеты, заметки, рекорды, блины и разминка, итог, восстановление после закрытия |
| Упражнения | 876 упражнений с фото (WebP, офлайн), русские названия, техника и ошибки, схема мышц, видео (поиск и закреплённая ссылка), история и график 1ПМ, свои упражнения |
| Программа | мастер первого входа, «Всё тело ×3» под ограничения, версии и откат, календарь с футболом и правилом «ноги не рядом с футболом», разгрузка, входящие правки тренера |
| Прогресс | вес со средним за 7 дней и темпом, обхваты, питание, восстановление, аналитика, экспорт и импорт |
| Тренер | MCP-сервер для Grok, заметки, токены, сводка в буфер и вставка правки |

## Запуск

```bash
npm install
npm run dev          # разработка, http://localhost:5173
npm run build        # сборка в dist/
npm run preview      # посмотреть собранное
```

Проверки:

```bash
npm test               # юнит и интеграционные тесты (vitest, IndexedDB в памяти)
npm run test:db        # миграции, изоляция данных и MCP-сервер на временном Postgres
npm run e2e            # ключевые сценарии в Playwright, включая аудит доступности axe
E2E_BASE_URL=https://piotrgoncharuk.github.io/coach/ npm run e2e   # то же по живому адресу
npm run mcp:smoke      # Edge Function в настоящем Deno по HTTP (DENO=/путь/к/deno)
npm run lint
```

Данные справочника:

```bash
npm run exercises:data     # data/ → public/data/exercises.json (идёт в каждую сборку)
npm run exercises:images   # фото из открытой базы → public/exercise-img/*.webp
npm run icons              # иконки и splash-экраны
```

### Справочник упражнений

Источник — [free-exercise-db](https://github.com/yuhonas/free-exercise-db) (public domain), закреплён
по коммиту в `scripts/build-exercise-data.mjs`. В репозитории лежат исходный JSON базы, русские
названия всех 876 упражнений (`data/exercise-names-ru.tsv`) и подробная техника для 49 упражнений
программы и их замен (`data/exercise-details-ru.json`); у остальных инструкция показывается
в оригинале с пометкой.

Фото (1746 файлов, 22 МБ) в git не хранятся: CI сжимает их в WebP и кэширует по коммиту базы.
Приложение берёт фото со своего адреса — не с GitHub — и service worker держит их офлайн после
первого просмотра. UUID упражнений выводятся из id базы, поэтому совпадают на всех устройствах.

## Где оно живёт

Приложение выложено на GitHub Pages: **https://piotrgoncharuk.github.io/coach/**

Каждый коммит в `main` запускает `.github/workflows/deploy.yml`: тесты → сборка → выкладка.
Руками ничего делать не нужно.

Pages отдают проект из подкаталога `/coach/`, поэтому базовый путь задан в `vite.config.ts`
(константа `BASE`) и подставляется в ссылки сборки, манифест, область действия service worker
и в `basename` роутера. Правил переадресации у Pages нет, поэтому `scripts/spa-fallback.mjs`
кладёт копию оболочки в `404.html` — иначе прямая ссылка вида `/coach/profile` не открывалась бы.

`npm run test:db` в CI не запускается: ему нужен локальный Postgres. Гонять перед изменениями
схемы вручную.

## Переменные окружения

Файл `.env` в корне (пример — `.env.example`). В репозитории секретов нет и быть не должно.

| Переменная | Где | Зачем |
|---|---|---|
| `VITE_SUPABASE_URL` | клиент | адрес проекта Supabase |
| `VITE_SUPABASE_ANON_KEY` | клиент | публичный ключ, безопасен в браузере: доступ ограничен RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | **только сервер** | импорт справочника упражнений и MCP-сервер. Никогда не в `VITE_*` |

**Без этих переменных приложение работает.** Данные лежат в IndexedDB, правки копятся в очереди
отправки. Как только ключи появятся и будет выполнен вход, всё накопленное уедет на сервер:
при первом входе локальные записи переписываются на настоящего пользователя (`adoptLocalData`).

## Устройство приложения

```
src/domain/    чистые функции с тестами: 1ПМ, прогрессия, готовность, объём,
               блины, разминка, планировщик, разгрузка, слияние, таймер
src/lib/       Dexie (локальная база), очередь отправки, синхронизация, вход, тема, звук, wake lock
src/ui/        компоненты: кнопки, степперы, чипы, таймер отдыха, нижняя навигация
src/screens/   экраны
supabase/      миграции и тесты изоляции данных
scripts/       генерация иконок, тест базы
```

### Локальная база — источник правды

UI читает только IndexedDB, поэтому в зале без сети ничего не меняется. Запись в базу и запись
в очередь отправки идут **одной транзакцией**: состояния «сохранил, но отправить забыл» нет.

Синхронизация запускается при старте, возврате приложения на экран, появлении сети и после записи
данных. Фоновой синхронизации в Safari на iOS не существует — других поводов нет.

### Два времени у каждой строки

| Поле | Кто ставит | Зачем |
|---|---|---|
| `updated_at` | устройство | по нему решается конфликт (last-write-wins) |
| `server_updated_at` | сервер (триггер) | по нему идёт вычитка изменений |

Без этого разделения правка, сделанная офлайн вчера, получила бы при отправке сегодняшнее время,
и второе устройство её бы не заметило. Конфликт разрешается по времени устройства, при равных
метках выигрывает сервер — так два устройства сходятся к одному значению.

Побочный эффект: если часы на телефоне сильно врут, его правки будут выигрывать чаще. Для двух
личных устройств это приемлемо.

### Удаления нет

Физического удаления нет ни на одном уровне: строка помечается `deleted_at`. У роли `authenticated`
**не выданы права на delete** и **нет ни одной политики delete** — две независимые преграды.

## Схема базы

Все таблицы под Row Level Security с политикой `user_id = auth.uid()` (у профиля — `id`,
у упражнений — `owner_id`). `force row level security` включён, то есть правило действует и на владельца таблицы.

| Таблица | Что хранит |
|---|---|
| `profiles` | рост, цели по ккал и белку, тема, ограничения здоровья |
| `exercises` | справочник: общие строки (`owner_id is null`, только чтение) и свои упражнения |
| `user_exercise_prefs` | заметка по упражнению, своё видео, свой отдых |
| `programs`, `program_days`, `program_exercises` | программа с версиями и откатом |
| `calendar_events` | зал, футбол, отдых: дата, длительность, тяжесть 1–10 |
| `sessions`, `session_exercises`, `sets` | тренировки и подходы (вес, повторы, RIR, тип) |
| `personal_records` | рекорды: вес, повторы, расчётный 1ПМ |
| `body_metrics` | вес и обхваты |
| `saved_meals`, `nutrition_entries` | питание: сохранённые блюда и записи за день |
| `readiness_checkins` | утренний чек-ин и посчитанная готовность |
| `coach_notes` | долговременная память тренера |
| `program_change_proposals` | черновики правок программы — единственный способ записи для ИИ |
| `api_tokens` | хэши личных токенов для MCP |

Применение миграций:

```bash
psql "$DATABASE_URL" -f supabase/migrations/0001_init.sql
```

Проверка изоляции данных (поднимает временный Postgres, применяет миграции, пытается прочитать
и изменить чужие строки):

```bash
npm run test:db
```

## Расчёты

Вся арифметика — чистые функции в `src/domain`, каждая с тестами.

| Что | Формула |
|---|---|
| Расчётный 1ПМ | Эпли: `вес × (1 + (повторы + RIR) / 30)`; при одном эффективном повторе — сам вес |
| Прогрессия | двойная: сначала повторы до верха диапазона, потом вес. Большой запас повторов удваивает шаг, два провала подряд — откат примерно на 10% |
| Осторожный режим | шаг не больше 2,5 кг, запас повторов не ниже 2, вес не растёт после подхода в упор (для спины и бедра) |
| Готовность | `75 + сон + энергия − боль − стресс − футбол за 72 ч`, 0–100. Зелёный ≥ 75, жёлтый 50–74, красный < 50 |
| Футбольная нагрузка | `минуты × тяжесть`, затухание: сутки — полностью, двое — половина, трое — пятая часть |
| Недельный объём | основная мышца — подход, вспомогательная — половина; разминка не считается |

## Что в PWA на iPhone не работает

Честно, без имитации:

| Требование | Как есть |
|---|---|
| Вибрация по окончании отдыха | **Невозможна.** Vibration API в Safari на iOS нет. Вместо неё — звук и крупная визуальная отметка |
| Звук, когда приложение свёрнуто | iOS останавливает вкладку. Таймер покажет верное время при возвращении (считается по метке времени), но сигнала в этот момент не будет. Поэтому на тренировке берётся Screen Wake Lock |
| Фоновая синхронизация | Background Sync в Safari нет. Синхронизация — по открытию, возврату на экран, появлению сети |
| Очистка хранилища | Safari может вычистить данные сайта после 7 дней без заходов. Для приложения с домашнего экрана риск близок к нулю, плюс запрашивается `navigator.storage.persist()` |
| Web Push | Только для приложения с домашнего экрана, iOS 16.4+. Отложено: напоминания делает тренер |

## MCP-сервер для тренера (Grok)

`supabase/functions/mcp` — Supabase Edge Function, протокол MCP 2025-06-18 поверх
Streamable HTTP. Сервер без состояния: один POST — один JSON-RPC запрос, ответ
`application/json`. GET → 405 (поток уведомлений не нужен).

**Авторизация** — личный токен из приложения (Профиль → Тренер): `Authorization: Bearer cch_…`.
В базе хранится только SHA-256 хэш, токен показывается один раз, отзывается там же.

**Изоляция.** Функция ходит в базу напрямую (`SUPABASE_DB_URL`), мимо RLS, поэтому
каждый запрос в `_shared/coachData.ts` фильтрует строки по `user_id` владельца токена.
Тест `npm run test:db` проверяет, что по токену Петра не видно ничего из данных Юлии.

| Инструмент | Что отдаёт / делает |
|---|---|
| `get_profile` | рост, ограничения, цели питания, шаблон недели, последний вес, правила планировщика |
| `get_program` | дни, упражнения (`exercise_id`, `slug`, название), подходы, `rep_min`/`rep_max`, `rir`, `rest_sec`, осторожный режим |
| `get_calendar(from, to)` | зал, футбол (`duration_min`, `intensity_1_10`), отдых |
| `get_sessions(from, to)` | тренировки: подходы (`weight_kg`, `reps`, `rir`, `type`, `e1rm_kg`), `duration_min`, `difficulty_1_10` |
| `get_exercise_history(exercise_id)` | история по датам, лучший 1ПМ за день, рекорды; id, slug или название |
| `get_weekly_summary(week)` | неделя с понедельника: сделано/запланировано, подходы, тоннаж, объём по группам, футбол, готовность, вес, питание, рекорды |
| `get_body_metrics(from, to)` | вес, кг и обхваты, см |
| `get_nutrition_summary(from, to)` | ккал и белок по дням, среднее, цели |
| `get_readiness(from, to)` | чек-ины и балл 0–100 с формулой |
| `propose_program_change` | **черновик** правки — программа не меняется, пока пользователь не примет её в приложении |
| `add_coach_note` | заметка тренера — его долговременная память, видна на главном экране |
| `get_coach_notes` | прошлые заметки |

Инструментов изменения и удаления записей нет — тренер физически не может их трогать.
Ошибки параметров возвращаются как результат с `isError: true` и причиной по-русски,
чтобы модель исправилась сама.

**Формат правки** (тот же принимает поле «Вставить правку от тренера»):

```json
{
  "title": "Фронтальный присед вместо классики",
  "rationale": "Поясница ноет третью неделю",
  "changes": [
    { "op": "replace_exercise", "day": 1, "exercise": "Barbell_Squat", "with": "Front_Barbell_Squat" },
    { "op": "update_exercise", "day": "День B", "exercise": "Face_Pull", "sets": 4 },
    { "op": "add_exercise", "day": 3, "exercise": "Plank", "sets": 3, "rep_min": 30, "rep_max": 45, "rir": 2 }
  ]
}
```

`op`: `update_exercise`, `add_exercise`, `remove_exercise`, `replace_exercise` (`with`),
`move_exercise` (`position`), `update_day` (`name`, `heavy_legs`). `day` — номер с 1 или название.
Правка применяется целиком или никак; принятая становится новой версией программы.

### Развёртывание

```bash
supabase link --project-ref <ref>
supabase db push                                   # миграции из supabase/migrations
supabase functions deploy mcp --no-verify-jwt      # своя авторизация токеном, не JWT
```

Адрес сервера: `https://<ref>.supabase.co/functions/v1/mcp`. В Grok — удалённый MCP-сервер
с этим адресом и заголовком `Authorization: Bearer <токен из приложения>`.

### Проверки сервера

```bash
npm run test:db       # 17 проверок ядра MCP на настоящем Postgres, включая изоляцию
npm run mcp:smoke     # функция в настоящем Deno, запросы по HTTP (нужен DENO=/путь/к/deno)
```

### Запасной путь без MCP

Профиль → Тренер → «Сводка за 7 / 28 дней» копирует текст в буфер (числа с единицами,
программа со ссылками на упражнения, формат ответа в конце). Ответ тренера с JSON-правкой
вставляется в поле «Вставить правку от тренера» и попадает во входящие на вкладке «Программа».

## Как включить синхронизацию и тренера

Пока ключей нет, всё работает на устройстве. Чтобы данные жили на сервере и тренер их видел:

1. Создать проект в Supabase, в Authentication включить вход по email (magic link) и добавить
   `https://piotrgoncharuk.github.io/coach/` в Redirect URLs.
2. Применить миграции: `supabase db push`.
3. Загрузить общий справочник упражнений в таблицу `exercises` сервисным ключом (строки
   `public/data/exercises.json`, `owner_id = null`) — иначе подходы не пройдут внешний ключ.
4. В GitHub → Settings → Secrets and variables → Actions → **Variables** добавить
   `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` и перезапустить сборку — workflow их уже
   подхватывает. Service role key сюда не нужен и класть его нельзя.
5. Развернуть MCP: `supabase functions deploy mcp --no-verify-jwt`.
6. В приложении войти по ссылке из письма — записи с устройства уедут на сервер сами.
